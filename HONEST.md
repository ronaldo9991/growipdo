# What actually broke, and where the code still cheats

## What broke

The repo I was handed to "make run" did not exist: the folder was empty, the GitHub repo had no commits, and nothing on the machine matched, so I built the system from the brief before anything could run. The first thing the live model did was reject every request, because the gpt-5 family refuses `max_tokens` and non default temperature on chat completions and spends part of the completion budget on hidden reasoning, so the wrapper now sends `max_completion_tokens`, drops a parameter the server names as unsupported, remembers that per model, and raises the budget. Run 1 then produced a ledger that was wrong in three ways I could only see against your hand checked facts: the USD 1 billion figure came out verified because my tiering treated every page on adgm.com as a regulator finding when that page is a co-branded company announcement; a true register claim was refused because the lexical retriever ranked the fine notices above the register row the claim came from; and five expected claims never existed because the claim cap filled up with register boilerplate before the Forbes page or the funding blog got a turn. I also found that your premise on the 144 investors and USD 2.1 million figure was wrong: it is not a press number, the ADGM notice states it, while the DFSA notice says over 150 and USD 2 million, so two regulators give different figures for the same offer and the system verifies both and notes the discrepancy. Run 3 died outright on one claim because the model wrote excerpt ids as bare tokens, `[E1,E2]`, twice in a row; the parser now repairs that one pattern and a pass that still fails twice refuses that claim with the error as its reason instead of losing the run. The extractor invented "Sarwa was included in Forbes 2026 Fintech 50" from a Forbes US page that never mentions Sarwa; verification caught it, and the extractor now requires the quoted sentence to exist in the page and skips pages that never name the subject. Forbes Middle East's list page says in its footer that all data was provided by the companies, so profile facts there are now treated as the company's word and only the placement counts as Forbes's own finding. GlobeNewswire refuses even curl from this connection within half a second and times out from the Railway server in another region too, so the company's 8 May 2026 release, the only place the "Top 20" wording and the USD 25 million funding claim live, is recorded as could not check on both machines; the same USD 25 million claim reaches the ledger through an aggregator and is correctly refused as press only, and the "Top 20" wording never enters the ledger at all, which is a gap in coverage, not a wrong verdict. On the deployment side, the Railway CLI panics on `railway volume add`, so the volume is created through Railway's GraphQL API with the CLI's own token, and pushing to GitHub redeploys the service, which would have killed the deployed run had I pushed mid run. What I would fix next: flag when two verified findings from different primary sources disagree on the same event, which the system currently leaves for the reader to notice; and run the verification passes concurrently, because 72 claims times two passes is most of the six to seven minute wall clock.

## Where the code still cheats or is weak

- Retrieval is lexical: idf weighted term overlap, exact number bonus, bigram bonus, and a guaranteed passage from the claim's origin page. No embeddings. A paraphrased fact in a page can still be missed, which turns a true claim into a refusal.
- Source tiers are decided by URL rules in `app/config.py` and `app/research.py`, plus the model's judgement of whether an excerpt relays the company's word. A regulator page with an unusual URL can be mis-tiered.
- Dedupe across press syndication is token Jaccard over claim text with a number match shortcut. Two rewrites of the same release can survive as two claims.
- Cross source disagreement between two verified findings (over 150 versus 144 investors) is noted inside a finding's discrepancy field but not raised as its own warning.
- Filler words are linted, the model is asked once to rewrite, and only em dashes and hashtags are repaired mechanically. A filler word that survives the rewrite is shown as a warning on the draft, not removed.
- Verification is single threaded. Fetching is parallel; the model calls are not.
- The claim budget is a cap (72) filled round robin by tier, three per source per lap. Which claims from a rich page make the cut depends on the extractor's ordering.
- The model that extracts claims is the weaker one, and a bare `[E1,E2]` style JSON slip is repaired by a regex rather than by a schema enforced response format.
- Table rows in fetched HTML are joined with separators, but there is no PDF parsing, no JavaScript rendering, and a 403 is recorded as could not check without a second attempt under a different identity, on purpose.
- The identify stage trusts search snippets plus one model call with a 0.6 confidence floor. A common name with a namesake in the same industry could be resolved wrongly, and nothing but the human gate would catch it.
- Evidence snapshots live under `evidence/` locally but under the volume at `/app/runs/evidence` on Railway, so the server's audit trail is not in git; the deployed run's ledger, log and diagnostic were copied back by hand into `runs/deployed-20260913-143149-a339/`, its page snapshots were not.
- The web pages are rendered from `ledger.json` by plain JavaScript with no build step. There is no authentication on the approve endpoint: anyone with the URL can sign a draft with any name.
- Runs are not deterministic. Five local runs of the same URL gave between 25 and 35 verified findings, because search results shift, the claim cap is filled in extractor order, and the models are not seeded. The verdict rules are fixed; what gets checked is not.
